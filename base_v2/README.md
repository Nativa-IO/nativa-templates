# Nativa Base V2

Template base para proyectos Nativa con React + Vite, FastAPI y Docker.

## Qué cambia respecto a base_v1

En sesión, el preview **no tiene imagen propia**: corre sobre la misma imagen
que el runner de la IA (`NATIVA_RUNNER_IMAGE`, la escribe nativa-agent en el
`.env` del preview). Mismo Node, mismas toolchains, mismo uid. Nada que
construir para levantar o promover una sesión.

Las dependencias viven dentro del worktree (`frontend/node_modules`,
`backend/.venv`) y se instalan desde stores compartidos por caja:

- Frontend: **pnpm** (`pnpm-lock.yaml`), store en `/opt/cache/pnpm`.
- Backend: **uv** (`uv.lock`), caché en `/opt/cache/uv`.

Un promote solo enlaza desde el store lo que la IA ya instaló en el runner:
segundos, sin red. Sin volúmenes anónimos de `node_modules`.

Producción sigue horneando una imagen inmutable (`docker/*.Dockerfile`).

## Runtime

El `docker-compose.yml` de la raiz esta pensado para preview/smoke tests:

- Frontend: `npm run build` durante el build de imagen y `npm run preview` al arrancar.
- Backend: `uvicorn app.main:app --host 0.0.0.0 --port 8000`, sin `--reload`.
- Database: no se levanta Postgres por sesion; `DATABASE_URL` debe apuntar a la DB del proyecto.
- Networking: los servicios usan `expose` y labels de Caddy. No publican puertos al host.

## Variables

La raiz del proyecto debe tener un `.env` con al menos:

```env
DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/DB_NAME
PROJECT_NAME=Nativa App
API_V1_PREFIX=/api/v1
SECRET_KEY=change-me
ACCESS_TOKEN_EXPIRE_MINUTES=1440
ALGORITHM=HS256
```

Para routing via Caddy/Nativa:

```env
PUBLIC_FRONTEND_HOST=session.workspace.preview.devnativa.com
PUBLIC_API_HOST=api-session.workspace.preview.devnativa.com
CADDY_INGRESS_NETWORK=nativa-ingress
```

## Comandos Locales

Frontend (pnpm, fijado por `packageManager` en package.json — `corepack enable`):

```bash
cd frontend
pnpm install --frozen-lockfile
pnpm run dev
pnpm run build
```

Backend (uv):

```bash
cd backend
uv sync --frozen
uv run uvicorn app.main:app --reload
```

## Docker

Para levantar el stack de preview/smoke:

```bash
docker compose up --build
```

Para detenerlo:

```bash
docker compose down
```

## El health de cada servicio

`.nativa/manifest.json` (versión 2) declara cómo sabe el agente que un servicio está
listo y sigue vivo. El sondeo corre **dentro de la red de compose**, contra el
nombre del servicio (`http://backend:8000/health`) — nunca contra el dominio
público, para que el health no dependa de Caddy, DNS ni del túnel.

```json
"health": {
  "type": "http",
  "port": 8000,
  "path": "/health",
  "method": "GET",
  "expect_status": [200],
  "timeout_ms": 2000,
  "interval_ms": 3000,
  "retries": 3,
  "start_period_ms": 120000
}
```

Cuatro tipos, como en Kubernetes y Docker:

| `type` | Campos propios | Sano cuando |
|---|---|---|
| `http` | `port`, `path`, `method`, `scheme`, `headers`, `expect_status` | El status está en `expect_status` (default 200–399) |
| `tcp` | `port` | El socket abre |
| `exec` | `command` (arreglo, sin shell) | El código de salida es 0 |
| `none` | — | No se sondea: listo al arrancar |

Los tiempos son iguales para todos los tipos:

| Campo | Default | Qué significa |
|---|---|---|
| `timeout_ms` | 2000 | Cuánto espera una prueba antes de contarla fallida |
| `interval_ms` | 3000 | Cada cuánto se repite |
| `retries` | 3 | Fallos seguidos para declararlo caído |
| `start_period_ms` | 60000 | Gracia inicial: los fallos no cuentan, solo retrasan el "listo" |
| `success_threshold` | 1 | Éxitos seguidos para volver a sano |

Reglas del endpoint:

- **Sin auth y barato.** Nada de tocar la base en cada sondeo; para eso usa
  otro endpoint (`/health?deep=1`), no el del sondeo.
- **Falla cerrada.** Un `type` desconocido o un campo inválido es error de
  manifiesto: el servicio queda en error, nunca en verde.
- **Compatibilidad.** Un `health` viejo (`{port, path}`) se lee como
  `type: "http"` con los defaults.
